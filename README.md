# 📺 TV投屏 (TVCast)

局域网电视投屏工具 —— 电脑 + 手机双端遥控。

投屏原理和 iPhone 的"推送地址"是同一路子：本机只把
`http://192.168.x.x:18632/media/xxx.mp4` 这个地址告诉电视，电视自己去拉流。
**电影不上云、不上传。**

---

## 两个端

| 端 | 打开方式 | 能干什么 |
| --- | --- | --- |
| **电脑端**（主程序） | 双击 `TVCast.exe` | 选片源、扫设备、投屏、遥控；显示手机遥控网址 + 二维码 |
| **手机端**（网页遥控器） | 手机浏览器打开 `http://本机IP:18632/` | 扫设备、翻目录/搜片、投屏、播放/暂停/停止、音量、拖进度 |

手机端**不需要装任何 App**，扫码即用。两端共用同一份状态，改一个另一个 1~2 秒内同步。

> 手机和电脑必须在**同一个 Wi-Fi** 下。

---

## 快速开始

**方式一：图形界面（推荐）**

双击 `TVCast.exe`：

1. 左侧选片源（默认是当前用户的「视频」文件夹；换过一次目录就会记住），会递归列出所有视频，按体积排序
2. 点「🔍 扫描局域网电视」
3. 选片 + 选电视 → 点「▶ 开始投屏」
4. 手机扫右侧二维码，或浏览器打开显示的网址 → 用手机遥控

**方式二：只跑服务端（无窗口，适合丢后台/开机自启）**

```bash
TVCast.exe --web --root "D:\Videos" --port 18632
```

**注意：程序必须保持运行，关掉电视就拉不到流了。**

## 手机网页遥控器 · 接口一览

程序内置的 HTTP 服务一个端口干三件事（默认 `18632`）：

| 路径 | 说明 |
| --- | --- |
| `GET /` | 手机遥控网页 |
| `GET /media/<相对路径>` | 媒体流（支持 Range，供电视回连拉流） |
| `GET /api/state` | 当前状态（设备 / 文件 / 进度 / 音量 / 播放状态） |
| `POST /api/scan` | 扫描设备 |
| `POST /api/select` | `{key}` 选择设备 |
| `GET /api/browse?dir=` | 列目录 |
| `GET /api/search?q=` | 搜索片名 |
| `POST /api/cast` | `{rel, device_key}` 投屏 |
| `POST /api/action` | `{action, value}`，action ∈ play/pause/stop/seek/volume |
| `GET /api/analyze?rel=` | 单个文件的编码信息 + 能否直连 |
| `GET /api/analyze_dir?dir=` | 批量探测目录内文件（带时间预算 + 后台预热） |
| `GET /live/<相对路径>.ts` | **实时转码流（MPEG-TS）** —— DLNA 电视走这条；加 `?t=秒数` 表示从该时间点起转（拖进度条用） |
| `GET /stream/<相对路径>` | 实时转码流（fragmented MP4）—— Chromecast 走这条，同样支持 `?t=` |
| `POST /api/transcode` | `{rel}` 整片转码到缓存，可拖进度 |
| `GET /api/transcode/status` | 转码进度 / 剩余时间 |
| `POST /api/transcode/cancel` | 取消转码 |
| `POST /api/config` | `{auto_transcode, force_transcode}` |

> 安全提示：接口**无鉴权**，局域网内任何人访问该端口都能操作。
> 仅建议在自家/可信网络里用；不要把这个端口映射到公网。

## ⭐ 格式兼容与自动转码

**这是最容易踩的坑。** 电视（尤其 DLNA）能直接播的格式窄得可怜：

```
MP4 容器 + H.264 (8bit, yuv420p) + AAC-LC 立体声
```

其他一律"暂不支持该内容格式"。最常见的元凶是 **AV1 / VP9 视频**和 **AC3 / DTS / Opus 音频**
（从视频网站下载的片子基本都是 `AV1+Opus` 或 `VP9+Opus`）。

程序会自动判断每个文件，并分三条路走：

| 情况 | 处理 | 能拖进度吗 |
| --- | --- | --- |
| 本来就兼容 | **直连**推原始文件 | ✅ 能（取决于电视固件），不耗 CPU |
| 不兼容，开了「兼容模式」 | **实时转码**：ffmpeg 边转边推，**同一条流边播边缓存** | ✅ 能，拖动即从该点**重新起流**（见下节） |
| 已经缓存过 | 直接用 `<媒体目录>/.tvcast_cache/` 里的 MP4 | ✅ 能，秒开 |
| 不想等、又想彻底秒开 | 点「⚡ 转码成 MP4」整片转完再投 | ✅ 能 |

手机网页上每个文件都有徽标：`直连` / `需转码` / `缓存✓`。

### ⚠️ 直播流为什么要用 MPEG-TS 而不是 MP4

这是**实测踩出来的关键坑**，写下来免得以后改错：

实时转码最初输出的是 **fragmented MP4**（`-movflags frag_keyframe+empty_moov`），
结果电视（Android stagefright）**拿到流 2 秒内就断开**，表现为"怎么都投不上"。

抓包看到电视发的是：

```
GET /stream/xxx.mp4   Range: bytes=0-      ← 先拉一次
GET /stream/xxx.mp4   Range: bytes=2700-   ← 又想要"从第 2700 字节开始"（在找 moov 索引）
```

`empty_moov` 的分片 MP4 **时长 0、没有 moov 索引**，电视按"可随机读"的方式去访问却拿不到
对应字节，于是直接放弃。换成 **MPEG-TS** 后一次通过 —— TS 天生是流式容器，不需要索引。

所以：

| 目标设备 | 直播流容器 | 地址形态 |
| --- | --- | --- |
| DLNA 电视 | **MPEG-TS**（`video/mp2t`） | `/live/<路径>.ts` |
| Chromecast | fragmented MP4 | `/stream/<路径>` |

> 顺带一提：URL 结尾的 `.ts` **不能省** —— 播放器会按扩展名判断容器类型。

### 直播流没有"时长"怎么办

TS 直播流本身不含可读的时长，电视也不会回报进度，界面上会一直是 `0:00 / 0:00`。
程序的做法是：**总时长取源片时长**（ffprobe 已知），**已播时长按"流起点 + 播放墙钟"估算**
（电视按 1 倍速播，两者基本一致）。桌面上会标一个"转码定位"，手机网页上进度条正常走、**也能拖**。

### 转码播放时怎么拖进度条（重推定位）

实时转码推出的是一条"活"的流，里面**没有索引也没有时长**，播放器根本无处可定位；
DLNA 的 `Seek` 动作对这种流也不会生效。所以拖动进度条的做法是**让服务端从目标时间点
重新起一条流，再把新地址推给电视**：

```
手机拖进度条 → POST /api/action {action:"seek", value:秒}
            → core.seek_live()       ※ 不调 dlna.seek()，它必然失败
            → cast(start=目标秒)     → 新 URL 变成 /live/<路径>.ts?t=目标秒
            → SetAVTransportURI + Play
            → 旧转码进程被掐掉，电视从该时间点重新拉流
```

关键点：

- `?t=N` 落到 ffmpeg 上是 **`-ss N`（放在 `-i` 之前）**，属于快速定位，回连约 0.5~2 秒（NVENC）
- 定位**不会命中缓存**：缓存是从头转的那一份，时间点对不上（`start > 0` 时强制走重推）
- 同一条片子会先把上一轮转码进程掐掉，避免两个 ffmpeg 同时抢编码器
- 手机端对拖动做了 180ms 防抖，避免一次拖动打出十几个定位请求
- ⚠️ 拖动定位会**中断这次的"边播边缓存"**（半截流会被丢弃），想吃缓存就从头一次播完
- ⚠️ 电视自己那根进度条仍然是"直播"状态（TS 无索引，改不了）；**能拖的是手机遥控端和桌面端的进度条**

### 边播边缓存（默认行为）

实时转码那条流在推给电视的**同时顺便落一份盘**，播完后自动重新封装成标准 MP4
（只做 `-c copy` 重新封装，**不重新编码**，几秒钟完成）。
于是同一部片子：**这一次是秒开，下一次就是秒开 + 能拖进度**。

- 只对"从头播放"的流生效；中途续播（`?t=秒数`）不缓存，避免存下半截片子
- **中途停掉不会留下缓存**——半截文件会被丢弃，免得下次误当成完整影片
- 封装进度会显示在手机网页的片源信息行：`正在封装缓存` → `缓存已就绪，下次秒开可拖`

**转码用什么加速**：自动挑 `h264_nvenc`（NVIDIA 显卡）→ `h264_qsv`（Intel 核显）→ `libx264`（CPU）。
在带 NVIDIA 独显的机器上实测 12~22 倍速，也就是说 1 小时的片子约 3 分钟转完，**实时转码绰绰有余**。

**依赖**：需要系统里有 `ffmpeg` 和 `ffprobe`（建议 5.0 以上）。
找不到的话转码功能会自动禁用并在界面提示；也可以把路径写进
`%USERPROFILE%\.tvcast\config.json` 的 `ffmpeg` / `ffprobe` 字段。

同一个配置文件里还有个 `root` 字段，记录**上一次选择的媒体目录**（在界面里换过目录就会自动写入）。
也可以用环境变量 `TVCAST_ROOT` 指定媒体目录，它优先级最高。

> 转码缓存放在媒体目录下的 `.tvcast_cache/`（以点开头，不会出现在片源列表里）。
> 不需要了直接删这个文件夹即可，不会影响原片。
>
> **注意体积**：AV1/VP9 是很省的编码，转成 H.264 后文件通常会**变大**（实测一集 25 分钟的
> 卡通片缓存后约 500MB）。看完整季会占不少空间，定期清一清即可；
> 也可以把 `.tvcast_cache` 整个删掉，下次再看会自动重新生成。

## 常见问题

**扫描不到电视？**
- 电视和电脑必须在**同一个局域网**（同 Wi-Fi / 同交换机；跨网段、访客网络、开了 AP 隔离的通常不行）
- 安卓电视请在设置里开启「投屏 / 屏幕镜像 / DLNA / 多屏互动」
- Windows 防火墙可能拦截，把本程序设为允许（专用网络）

**手机打不开网页？**
- 确认手机连的是**同一个 Wi-Fi**（不是 4G/5G，也不是别的网段）
- 确认地址里的 IP 就是电脑的局域网 IP（界面右上角有显示）
- 电脑防火墙放行 `18632` 端口（专用网络）

**电视提示"暂不支持该内容格式"？**
- 看手机网页上那个文件的徽标。如果是 `需转码`，确认「兼容模式」是打开的，重新投屏即可
- 转码播放中手机端进度条**可以拖**，拖动后约 1 秒从新位置重新起流
- 想彻底秒开、拖动无感，就点「⚡ 转码成 MP4」，转完再投屏
- 如果徽标显示 `直连` 却仍播不了，多半是**分辨率/码率超出电视能力**（比如 4K 高码率），
  这种情况打开「强制转码」让它重编一遍

**点投屏后电视完全没反应 / 一直投不上？**
- 先看**日志区**：找出真实原因（扫描/连接/转码/推送各自会打日志）
- 电视上**没有任何变化，且日志显示"已推送"** → 说明指令到了但电视不去拉流。
  按这个顺序查：
  1. 电视的 DLNA/投屏开关是否打开
  2. 电视和电脑是否在**同一个网段**（都连同一个路由器/AP，别一个走 WiFi 一个走手机热点）
  3. 电脑防火墙是否放行本程序（Windows 网络若被归为"公用网络"，入站会被拦；
     程序首次运行时应允许"专用网络 + 公用网络"）
  4. 该文件是不是需要转码（看徽标）——不兼容格式靠自动转码解决
- **流格式不匹配**（曾经的最大坑）：详见上面「直播流为什么要用 MPEG-TS 而不是 MP4」

**能拖进度条吗？**
- 直连播放：本机媒体服务实现了 HTTP Range，理论支持；但**能不能拖最终取决于电视固件**
- 实时转码：**能拖**。拖动后由服务端从该点重新起一条流转码再推给电视（约 1 秒）
  → 同一条流还会**边播边缓存**，播完之后再放一次就是秒开 + 原生可拖
- 转码缓存：能拖，秒开

**为什么转码时拖进度要"重新起流"？**
- 能原生拖的前提是播放器能按字节偏移随机读（HTTP Range），这要求服务端有个**固定长度的完整文件**
- 实时转码时文件还没生成完，长度未知，电视自然没法定位 —— 这是协议层面的限制
- 所以转码播放的定位由**服务端重新起一条 `?t=N` 的流**来完成：不是让电视快进，而是让它改播"从 N 秒开始的另一条流"
- 想要完全无感的拖动，还是先整片转完（点「⚡ 转码成 MP4」）最舒服

**同时开了两个程序，手机地址变了？**
- 端口 18632 被占用时程序会自动换端口（避免 Windows 上 `SO_REUSEADDR` 抢占端口的坑），
  界面和日志里会提示。关掉多余的那个实例即可。

## 源码结构

```
tvcast/
  util.py        本地 IP / MIME 猜测 / 格式化
  httpserver.py  一体化 HTTP 服务（网页 + API + 媒体流 + 转码推流）
  webui.py       手机网页遥控器（单文件 HTML，离线可用）
  core.py        核心控制层（设备 / 片源 / 播放状态 / 遥控动作 / 选路）
  media.py       格式判定 + 转码引擎（ffprobe 分析 / 实时转码 / 缓存转码）
  discovery.py   SSDP 发现 DLNA + mDNS 发现 Chromecast
  dlna.py        DLNA AVTransport / RenderingControl（纯标准库 SOAP）
  cast.py        Chromecast 控制（pychromecast）
  app.py         tkinter 图形界面（含二维码）
main.py          入口（GUI / --web / --scan / --cast）
tests_env.py     回归测试脚本共用的环境配置（个人相关的值全部走环境变量）
```

GUI 和网页都只调 `core.py`，所以两端状态天然一致。

## 重新打包

```bash
# 一次性准备环境（已存在 .venv 可跳过）
uv venv .venv --python 3.12
uv pip install --python .venv/Scripts/python.exe -r requirements.txt

# 出包（配置都在 TVCast.spec 里）
.venv/Scripts/python.exe -m PyInstaller TVCast.spec --noconfirm
```

> 打包前**必须先关掉正在运行的 TVCast.exe**：PyInstaller 要删掉旧的 `dist/TVCast.exe`，
> 文件被占用时会失败。若删除被环境的"安全回收站"拦住（回收站不可用的盘会这样），
> 就把旧 exe **改名挪走**再打包（重命名不触发回收站）：
> `mv dist/TVCast.exe dist/TVCast.exe.bak` → 打包 → 再清理备份。
>
> 顺带两个 Windows 坑：
> - 手动跑 `--clean` 会清掉 `build/`，但不会帮你处理被占用的 `dist/` 产物
> - `TVCast.exe` 是 onefile 结构（父进程 + 子进程），杀进程要用 `taskkill /PID x /T /F`，
>   只 `terminate()` 父进程会留下孤儿进程继续占端口、拉起 ffmpeg

## 已踩的坑

**pychromecast 14.x**
- `Chromecast` 对象**没有** `set_volume`，音量在 `c.socket_client.receiver_controller` 上
- 音量字段是 `status.volume_level`（0.0~1.0），不是 `status.volume`
- `play_media` 默认 `stream_type=LIVE`，本地文件必须显式传 `STREAM_TYPE_BUFFERED`，
  否则电视按直播处理 —— 拿不到总时长、不能拖进度

**SSDP**
- 要**一次性发出全部 M-SEARCH 再统一收**，不能每个 ST 各等一轮超时（否则扫描要十几秒）

**转码流定位**
- 直播流转码（TS/fMP4）**没有索引**，`dlna.seek()` 对它必然失败 —— 定位只能"重推一条新流"，
  即把 URL 换成 `?t=N`、从头重开一路 ffmpeg。别想着让电视自己快进。
- 进度基准必须是"**这一路流的起点**"（`_live_offset`）+ 播放墙钟，不能用"本集播了多久"。
  切换/定位时统一走 `_reset_watch(live_offset=…)` 重置，否则定位后进度会跳回 0。
- 定位时**不能命中转码缓存**：缓存是从头转的那一份，时间点对不上。判据是 `start > 0`。
- 同一条片子重推前要**掐掉上一路 ffmpeg**：电视若没及时断开旧连接，会出现两个 ffmpeg 抢编码器。
  被 `kill()` 掐掉的那一路 `returncode != 0`，所以它不会把半截流误封成缓存（这个分支要保住）。
